# Automatic update prompt

## Objective

When a user starts an interactive `agent` session from an installed release
binary, check GitHub Releases for a newer stable version before constructing the
session. If one exists, show a Codex/Claude Code-style picker that clearly shows
the current and target versions and lets the user update, skip this launch, or
exit.

The check must never delay non-interactive automation or prevent an interactive
session from starting when GitHub is unavailable.

## Tech stack

- Go standard library for HTTP, JSON, archives, hashing, files, and version
  comparison.
- Bubble Tea/Lip Gloss, already used by the project, for the interactive picker.
- GitHub repository `xautjzd/agent-cli` and GoReleaser assets generated by
  `.goreleaser.yml`.

## Commands

- Build: `go build ./cmd/agent`
- Focused tests: `go test ./internal/update ./cmd/agent`
- Static checks: `go vet ./internal/update ./cmd/agent`
- Full tests: `go test ./...`

## Project structure

- `internal/update/`: release lookup, semantic version comparison, archive and
  checksum validation, atomic executable replacement, and update picker.
- `internal/update/*_test.go`: HTTP, archive, checksum, version, and picker
  regression tests.
- `cmd/agent/main.go`: interactive-only startup gate.
- `docs/automatic-updates.md`: public behavior and implementation contract.

## Code style

Use small typed boundaries and dependency injection for external effects:

```go
checker := update.Checker{Client: client, Repository: update.Repository}
release, available, err := checker.Latest(ctx, version.Version)
```

Network and filesystem failures return descriptive errors to the update layer;
the startup gate decides whether to continue, update, or exit.

## Testing strategy

- Table tests for release version ordering, including `v` prefixes and
  prerelease rejection.
- `httptest` coverage for success, timeout/error, response limits, unstable
  releases, redirect policy, and missing or malformed checksums.
- Temporary archives and checksums for successful install, checksum mismatch,
  unsafe archive paths, and atomic replacement failure.
- Picker model tests for displayed `current → latest` versions and all three
  choices.
- Startup tests proving subcommands, `-p`, piped input, disabled checks, and
  development builds never perform a lookup.

## Boundaries

- Always: HTTPS, fixed repository, short timeout, bounded responses/downloads,
  checksum verification, safe archive paths, same-directory temporary file,
  permission preservation, atomic replacement, and cleanup.
- Ask first: changing the repository, accepting prereleases, adding background
  processes, or introducing another dependency.
- Never: execute a downloaded shell script, invoke a shell with remote input,
  request sudo, overwrite the running binary before verification, or block
  startup because the update service is unavailable.

## Design rationale

The automatic path downloads only versioned assets from this repository's
GitHub Releases, verifies the archive against the release checksum, and performs
one same-filesystem rename after the replacement is complete. It does not run
the convenient shell installer shown for manual recovery because executing
fresh remote script content during every update would add avoidable risk.

GoReleaser injects the release version into packaged binaries. Binaries installed
with `go install module@version` recover the same stable version from Go build
metadata; local checkout builds remain `dev` and do not offer to replace
themselves.

## Success criteria

- Interactive release startup checks for a newer stable release.
- The prompt renders `Update available! <current> → <latest>` and the latest
  release-notes URL.
- Choices are `Update now`, `Skip`, and `Exit`, navigable with arrows or
  `1`/`2`/`3`, with Enter accepting the highlighted option.
- Skip continues immediately and only affects the current launch.
- Exit ends cleanly without constructing the agent session.
- Update verifies `checksums.txt`, atomically replaces writable macOS/Linux
  binaries, never damages the installed binary on failure, then exits cleanly
  and asks the user to run `agent` again.
- Windows and unwritable installations receive a clear manual upgrade command.
- `AGENT_NO_UPDATE_CHECK=1`, non-interactive invocations, unavailable GitHub,
  and development builds continue without a prompt.

## Open questions
